# Contributing

Use focused changes with a concrete user-visible result. The engine lives here;
product interfaces and operator-specific deployment settings belong elsewhere.
Keep public engine operations independent of HTTP handlers, update the changelog
for behavior changes and document API changes alongside their implementation.

## Development environment

Use Go 1.27.2 (the security-patched CI/release toolchain; module minimum 1.26.9),
FFmpeg/ffprobe with libx264/AAC/libmp3lame, Python 3 and PostgreSQL 17. Platform
imports also need Node.js. Offline metadata tests use the same checksum-pinned
yt-dlp as the runtime:

```sh
curl --fail --show-error --location --proto '=https' --tlsv1.2 \
  https://github.com/yt-dlp/yt-dlp/releases/download/2026.08.19/yt-dlp -o /tmp/cutmy-yt-dlp
echo '1fa6733c37ea6fb51c99ad8fe785e7b7e5f3246c9b980230329d4fb72ed8d4d6  /tmp/cutmy-yt-dlp' | sha256sum --check
chmod 755 /tmp/cutmy-yt-dlp
export CUTMY_TEST_YTDLP=/tmp/cutmy-yt-dlp
```

A disposable local test database can be started independently from the application:

```sh
docker run --rm -d --name cutmy-core-test-db \
  -p 127.0.0.1:55432:5432 \
  -e POSTGRES_USER=cutmy -e POSTGRES_PASSWORD=test-only-password \
  -e POSTGRES_DB=cutmy_test postgres:17.11-bookworm
# Wait until PostgreSQL reports ready, then:
export TEST_DATABASE_URL=postgres://cutmy:test-only-password@localhost:55432/cutmy_test?sslmode=disable
make check-full
# Remove the disposable database when finished:
docker stop cutmy-core-test-db
```

Never point tests or benchmarks at a production database. Integration tests create
isolated temporary schemas, but require schema-creation permission. Keep the
actual DSN private. Media fixtures are synthetic and generated by FFmpeg; do not
commit large videos, user uploads, credentials or downloaded third-party media.

## Checks

`make check` runs formatting, vet, local documentation links, available tests and
build. Media/database/extractor tests can skip if their dependencies are absent;
this fast check is not a complete acceptance run. `make check-full` requires the
media tools, exact extractor pin and dedicated database, runs uncached race tests,
workflow validation and govulncheck, and verifies third-party notices. CI does the
same on Linux and makes no requests to public videos.

For a targeted change, run relevant tests first, then the full checks before
release. Fetching changes need URL/redirect/byte-limit/owner-isolation tests.
Trimming changes need stream and duration checks that distinguish requested and
actual copy boundaries. Queue/storage changes need recovery, fencing, accounting
and deletion-failure coverage. Avoid tests that merely repeat implementation.

Benchmarks must record revision, toolchain, CPU/scheduler configuration, fixture,
commands and raw results, with identical before/after conditions. Separate cache,
database and media timings; do not describe an allocation reduction as faster
whole-video export. See [performance](docs/performance.md). Public-platform checks
are opt-in, outside CI and must respect access restrictions.

## Submitting changes

Explain the problem, resulting behavior, verification and material limitations in
the pull request. Preserve old clients when adding API fields; explicitly document
incompatible changes. Keep logs/public errors free of cookies, signed media URLs,
passwords and raw subprocess diagnostics. Communicate respectfully and keep review
comments specific to the change.

Dependency upgrades require reachable vulnerability checks and regeneration of
[third-party notices](THIRD_PARTY_NOTICES.md):

```sh
python3 scripts/update-notices.py
make notices-check
```

Build/publication instructions are in [releases](docs/releases.md). Release archives
include dependency notices and require external FFmpeg. Native platform support
claims need actual native media/cancellation checks, not just cross-compilation.

## Reporting problems

Use the issue templates for bugs and feature requests. Include `cutmy version`,
source type, sanitized reproduction, ranges/options and expected/actual behavior.
Omit cookies, private URLs, tokens and user data. Vulnerabilities follow
[SECURITY](SECURITY.md) instead of a public technical report.
