# Contributing

Use focused changes with a concrete user-visible result. The engine lives here;
product interfaces and operator-specific deployment settings belong elsewhere.
Keep public engine operations independent of HTTP handlers, update the changelog
for behavior changes and document API changes alongside their implementation.

## Development environment

Choose tools for the component you are changing. Documentation-only changes can
run `make docs-check`; local engine/CLI work needs Go and FFmpeg/ffprobe. Database
and platform-import dependencies below are for the full server acceptance suite.
See the [repository map](docs/architecture.md) and
[documentation index](docs/README.md) before adding a new top-level guide.

Use Go 1.27.3 (the security-patched CI/release toolchain; module minimum 1.26.9),
FFmpeg/ffprobe with libx264/AAC/libmp3lame, Python 3 and PostgreSQL 17. Platform
imports also need Node.js. Offline metadata tests use the same checksum-pinned
yt-dlp as the runtime.

Install the pinned OpenAPI tooling in an isolated Python environment before
running the checks:

```sh
python3 -m venv .venv-contract
.venv-contract/bin/python -m pip install -r scripts/requirements-contract.txt
export PATH="$PWD/.venv-contract/bin:$PATH"
```

Then install the offline extractor:

```sh
curl --fail --show-error --location --proto '=https' --tlsv1.2 \
  https://github.com/yt-dlp/yt-dlp/releases/download/2026.08.19/yt-dlp -o /tmp/cutmy-yt-dlp
echo '1fa6733c37ea6fb51c99ad8fe785e7b7e5f3246c9b980230329d4fb72ed8d4d6  /tmp/cutmy-yt-dlp' | sha256sum --check
chmod 755 /tmp/cutmy-yt-dlp
export CUTMY_TEST_YTDLP=/tmp/cutmy-yt-dlp
```

A disposable local test database can be started independently from the application:

```sh
docker run --rm -d --name cutmy-core-test-db \
  -p 127.0.0.1:55432:5432 \
  -e POSTGRES_USER=cutmy -e POSTGRES_PASSWORD=test-only-password \
  -e POSTGRES_DB=cutmy_test postgres:17.11-bookworm
# Wait until PostgreSQL reports ready, then:
export TEST_DATABASE_URL=postgres://cutmy:test-only-password@localhost:55432/cutmy_test?sslmode=disable
make check-full
# Remove the disposable database when finished:
docker stop cutmy-core-test-db
```

Never point tests or benchmarks at a production database. Integration tests create
isolated temporary schemas, but require schema-creation permission. Keep the
actual DSN private. Media fixtures are synthetic and generated by FFmpeg; do not
commit large videos, user uploads, credentials or downloaded third-party media.

Use a filesystem with enough free space for temporary media, Go's build/module
caches and the disposable database. Check filesystem capacity as well as the
virtual disk allocation: an enlarged disk can still contain a smaller partition.
For concurrent full-source and installed-SDK runs, use separate test databases
and new temporary/output directories. Keep production data outside those paths.
See [artifact retention](docs/artifacts.md) for retained evidence and scratch cleanup.

## Checks

`make check` runs formatting, vet, local documentation links, OpenAPI/schema and
compatibility validation, available tests and build. Media/database/extractor
tests can skip if their dependencies are absent;
this fast check is not a complete acceptance run. `make check-full` requires the
media tools, exact extractor pin and dedicated database, runs uncached race tests,
workflow validation and govulncheck, and verifies third-party notices. It also
requires actual HTTP/OpenAPI fixtures and their Python tooling. CI does the same
on Linux and makes no requests to public videos.

For focused work, `make check-static` runs formatting, vet, documentation and API
checks without media or database acceptance. `make check-controls` runs the
native-result, SDK-runner, performance-protocol and release-tooling controls.
These groups are also used by `check` and `check-full`; their existing checks
and ordering are preserved. Controls use synthetic inputs and may launch small
test processes; passing them does not establish real media, package installation,
historical restoration or release-signature acceptance.

### Command map

Run these commands from the repository root. `GO` and `PYTHON` can select the
executables used by Make; the pinned CI/release Go toolchain is listed above.

| Task | Entry point | Scope and prerequisites |
| --- | --- | --- |
| Build or run available Go tests | `make build`, `make test` | Builds `bin/cutmy` or runs `go test ./...`; integration tests can skip without their tools/database. |
| Format and inspect Go | `make fmt`, `make fmt-check`, `make vet` | `fmt` rewrites Go files; `fmt-check` and `vet` inspect them. |
| Check documentation or schemas | `make docs-check`, `make api-check` | Python 3 for local Markdown links; API checks also need the pinned OpenAPI tooling above. |
| Inspect source without media/database acceptance | `make check-static` | Formatting, Go vet, documentation and API/schema checks; needs Go and pinned Python contract tooling. |
| Check a working tree | `make check` | Formatting, vet, docs, API/schema compatibility, runner controls, available Go tests and build. |
| Require source acceptance | `make check-full` | Adds required media/extractor/database prerequisites, uncached race tests, hosting controls, notices, workflow validation and vulnerability checks. |
| Exercise HTTP/OpenAPI fixtures | `make contract-check` | Runs `api-check` and `TestHTTPPublicContract`; needs the Python contract tooling and disposable `TEST_DATABASE_URL`. |
| Test SDK source | [SDK unit-test commands](#sdk-checks) | Python 3.10+ or Node 20.19+/npm; no API, database or media rendering. |
| Test installed SDKs | `make sdk-check SDK_REPORT_DIR=/tmp/new-cutmy-sdk-http-check` | Builds and installs both SDKs, then exercises real local media and API/worker flows; needs pinned build tooling, media tools and disposable `TEST_DATABASE_URL`. Use a new directory outside the checkout. |
| Check runners and evidence rules | `make check-controls`, `make hosting-controls-check` | The first groups native-result, SDK-runner, performance and release controls; hosting controls remain separate. These do not run the corresponding complete acceptance harnesses. |
| Check the recovery harness | `make recovery-controls-check` | Synthetic recovery-runner controls only; `recovery-check` runs these before the actual historical upgrade and restoration. |
| Check notices, workflows or dependencies | `make notices-check`, `make workflows-check`, `make vuln` | Notices use the tracked modules; workflow/vulnerability tools use the pinned versions in Makefile and need network access when fetching tools or vulnerability data. |
| Verify historical upgrade and restoration | `make recovery-check` | Separate Linux harness; needs full historical Git objects, media tools, PostgreSQL clients and disposable `RECOVERY_DATABASE_URL` with database-creation permission. See [recovery](docs/backup-recovery.md). |
| Measure retained-row storage capacity | `make storage-capacity-check STORAGE_REPORT_DIR=/tmp/new-cutmy-storage-check` | Opt-in Linux workload with disposable `TEST_DATABASE_URL`; sizes and evidence requirements are in [storage capacity](docs/storage-capacity.md). |
| Package an approved release tag | `make release VERSION=vX.Y.Z` | Clean tagged checkout and exact Go toolchain; builds CLI archives twice outside the checkout. Signing and publication follow the separate [release protocol](docs/releases.md). |

`make check-full` does not invoke the separate SDK, historical-recovery or
storage-capacity harnesses. The [Core checks workflow](.github/workflows/ci.yml)
runs the native source and installed-SDK matrices plus Linux HTTP/worker
acceptance. [Public self-hosting acceptance](.github/workflows/self-hosting.yml)
owns its disposable deployment and restoration checks. The
[archive workflow](.github/workflows/release.yml) and
[downloaded-release consumers](.github/workflows/release-consumer.yml) enforce the
existing packaging, signature and publication gates; local packaging alone does
not complete them.

### SDK checks

Python SDK tests require Python 3.10+; TypeScript SDK tests require Node.js
20.19+ and npm. These focused commands do not start the API or render media:

```sh
PYTHONPATH=sdk/python/src python3 -m unittest discover -s sdk/python/tests -v
npm --prefix sdk/typescript ci
npm --prefix sdk/typescript test
```

Installed-package acceptance additionally requires Go, FFmpeg/ffprobe and the
pinned Python build tooling. It builds and installs wheel/sdist/npm packages
outside the source tree and exercises real local media; `--http` also requires
the isolated `TEST_DATABASE_URL` and runs the API/worker workflow:

```sh
python3 -m pip install --require-hashes --only-binary=:all: \
  -r scripts/requirements-sdk-build.txt
python3 scripts/check-sdks.py --output /tmp/cutmy-sdk-check
# Use a fresh output directory for each run.
make sdk-check SDK_REPORT_DIR=/tmp/cutmy-sdk-http-check
```

Run these inside an isolated Python environment. CI requires installed-package
acceptance on all five native platforms and a separate HTTP acceptance run;
passing only source unit tests does not establish package installation or media
behavior. The [published 1.4.2 SDK distributions](docs/sdk.md#install-versioned-packages)
are signed GitHub release assets: a wheel, Python source archive and npm tarball.
Current source can contain unreleased fixes; a source version or GitHub release
does not imply publication to the PyPI/npm registries.

The runner checks for 2 GiB of free output space before building. Successful
runs retain packages, frozen examples and verification evidence while removing
their disposable installed consumers and CLI. Failed runs retain scratch for
diagnosis. The capacity check covers the output filesystem; Go caches and the
test database can use other filesystems and need their own headroom.

### Change-specific validation

For a targeted change, run relevant tests first, then the full checks before
release. Fetching changes need URL/redirect/byte-limit/owner-isolation tests.
Trimming changes need stream and duration checks that distinguish requested and
actual copy boundaries. Queue/storage changes need recovery, fencing, accounting
and deletion-failure coverage. Avoid tests that merely repeat implementation.

Benchmarks must record revision, toolchain, CPU/scheduler configuration, fixture,
commands and raw results, with identical before/after conditions. Separate cache,
database and media timings; do not describe an allocation reduction as faster
whole-video export. See [performance](docs/performance.md). Public-platform checks
are opt-in, outside CI and must respect access restrictions.

## Submitting changes

Explain the problem, resulting behavior, verification and material limitations in
the pull request. Preserve old clients when adding API fields; explicitly document
incompatible changes. Keep logs/public errors free of cookies, signed media URLs,
passwords and raw subprocess diagnostics. Communicate respectfully and keep review
comments specific to the change.

Dependency upgrades require reachable vulnerability checks and regeneration of
[third-party notices](THIRD_PARTY_NOTICES.md):

```sh
python3 scripts/update-notices.py
make notices-check
```

Build/publication instructions are in [releases](docs/releases.md). Release archives
include dependency notices and require external FFmpeg. Native platform support
claims need actual native media/cancellation checks, not just cross-compilation.

## Reporting problems

Use the issue templates for bugs and feature requests. Include `cutmy version`,
source type, sanitized reproduction, ranges/options and expected/actual behavior.
Omit cookies, private URLs, tokens and user data. Vulnerabilities follow
[SECURITY](SECURITY.md) instead of a public technical report.
